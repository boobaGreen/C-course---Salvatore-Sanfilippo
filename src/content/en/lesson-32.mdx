## The SDL skeleton: a window and an array of bytes

Salvatore does not remember the SDL calls by heart and says so openly: he had an LLM generate them, using it in place of the man pages. The starting program does only four things: `SDL_Init(SDL_INIT_VIDEO)`, `SDL_CreateWindow(...)` at 640x480, `SDL_GetWindowSurface()` to obtain the surface to draw on, and a loop that consumes events until `SDL_QUIT`, with an `SDL_Delay(16)` to approach 60 frames per second.

<Callout type="pro" title="No lock unless needed">
  The generated code wrapped every draw in `SDL_LockSurface` and
  `SDL_UnlockSurface`. Salvatore checks the `SDL_MUSTLOCK(surface)` macro: it
  returns **0**, so the surface can be read and written at any time. Both
  calls go away. Moral: don't copy boilerplate, verify what it actually does.
</Callout>

The interesting part is `surface->pixels`: a pointer to the frame buffer memory. Each pixel takes 4 bytes in **B, G, R, A** order (the machine is little endian) and each row is `surface->pitch` bytes long. Here `pitch` is exactly `width * 4`, but on some hardware it may include padding on the right: always use the value SDL gives you.

From here come three tiny functions: `pixel(surface, x, y, r, g, b)`, `clear(surface)` which `memset`s `pitch * height` bytes to zero, and `draw(surface)` which is called every frame before `SDL_UpdateWindowSurface()`.

<Callout type="warning" title="The first bug: a dirty frame buffer">
  On the first try a line appears that shouldn't be there. The surface memory
  is **not initialized**: it contains whatever was there before. A `clear()` at
  the start of every `draw()` fixes everything. Remember the memory lesson: C
  zeroes nothing for you.
</Callout>

## From gradient to circle: sine and cosine

The first drawing is a gradient: the red component grows with X, green with Y, blue stays fixed at 128. Salvatore tries to vary blue too, but the result is worse. The reason is geometric: we are mapping a **three-dimensional** color space (RGB) onto a **two-dimensional** screen (XY). Keeping one component fixed is the sensible choice.

Then come 100 white pixels at random coordinates: `x = rand() % width`. The remainder of a division by `n` is always between `0` and `n - 1`, so the pixel lands inside the window.

The decisive step is a loop where the angle `alpha` grows slowly and the pixel is drawn at:

```c
x = cx + sin(alpha) * 50;
y = cy + cos(alpha) * 50;
```

The result is a circle of radius 50 centered at `(cx, cy)`. Sine and cosine are the same function shifted by 90 degrees: for every angle they describe a point on the unit circle.

<Callout type="tip" title="Why the circle matters">
  Rotating a point means making it "walk" along the circle that passes through
  it and is centered at the origin. From this intuition comes the rotation
  formula: `x' = x·cos(a) − y·sin(a)`, `y' = x·sin(a) + y·cos(a)`. The sign of
  the angle only decides the direction, clockwise or counter-clockwise.
</Callout>

## The 3D model: a `struct` and 1000 points

A point in space is a structure of three `float`s:

```c
typedef struct { float x, y, z; } P3;
#define NUM_POINTS 1000
P3 Model[NUM_POINTS];
```

`create_model()` fills the array. First with random numbers from −50 to 50 (`-50 + rand() % 100`), then with a regular grid: X and Z from −10 to 10, Y fixed slightly below the viewer's eye. Drawing only X and Y the cloud looks flat: something is missing to make Z perceptible.

### Perspective in one line

A distant object looks smaller. So the X and Y coordinates must be **divided** by a factor that grows with depth:

```c
float zf = 1 + Model[j].z / 400;   /* 400: the "perspective zoom" factor */
int sx = cx + Model[j].x / zf;
int sy = cy + Model[j].y / zf;
```

With `z = 0` the divisor is 1 and the point stays put. With positive `z` (far away) the divisor grows and the point shrinks toward the center. With negative `z` (toward the viewer) the divisor drops below 1 and the point spreads out. The **400** controls how extreme the effect is: the larger it is, the flatter and more orthographic the scene.

## Rotation around the Y axis

Rotating in 3D around an axis is a 2D rotation on the other two coordinates. For the Y axis, Y does not change and the formula becomes:

```c
rotated[j].x = Model[j].x * cos(alpha) + Model[j].z * sin(alpha);
rotated[j].y = Model[j].y;
rotated[j].z = -Model[j].x * sin(alpha) + Model[j].z * cos(alpha);
```

Two design details matter as much as the formula:

1. **Never rotate the model in place.** A second array `rotated[]` is recomputed from the original model every frame. Rotating the same points over and over would accumulate floating-point error.
2. **The angle depends on time.** A `time` counter grows by 1 every frame, and `alpha = time * (2π / 60) * 0.15`: at 60 fps one full turn per second, scaled to 15% for a slow rotation. Salvatore gets the math wrong the first time (dividing instead of multiplying) and fixes it by counting frames out loud.

<Callout type="pro" title="The ghost line">
  Before rotation, translating the model into depth makes a denser vertical
  line of points appear at the center. It is not a numeric error: grid points
  with `x = 0` stay exactly at `x = 0` after perspective and **collapse onto a
  line**, while all the others spread out. As soon as rotation moves them, the
  artifact disappears. Understanding an artifact is often more instructive
  than removing it.
</Callout>

<CodeEditor
  initialCode={`#include <stdio.h>
#include <math.h>

typedef struct { float x, y, z; } P3;

/* Rotation around Y + perspective projection, as in the video. */
void project(P3 p, float alpha, float k, int cx, int cy, int *sx, int *sy) {
    float rx =  p.x * cosf(alpha) + p.z * sinf(alpha);
    float rz = -p.x * sinf(alpha) + p.z * cosf(alpha);
    float zf = 1 + rz / k;
    *sx = cx + (int)(rx / zf);
    *sy = cy + (int)(p.y / zf);
}

int main(void) {
    P3 p = {100, 20, 0};
    int sx, sy;
    project(p, 0.0f, 400, 320, 240, &sx, &sy);
    printf("alpha=0    -> (%d, %d)\\n", sx, sy);
    project(p, 3.14159f / 2, 400, 320, 240, &sx, &sy);

## Persistence of vision: `fade()` instead of `clear()`

The final touch is a demoscene effect. Instead of zeroing the frame buffer, `fade()` walks all `pitch * height` bytes and lowers them:

```c
for (int j = 0; j < num_bytes; j++) {
    if (fb[j] > 15) fb[j] -= 15; else fb[j] = 0;
}
```

Pixels drawn in previous frames fade gradually and moving points leave a trail. The first attempt (`fb[j] /= 2`) turns everything off in a few frames and nothing is visible; subtracting a small constant makes the trail long and readable. With the random cloud enlarged to ±150 the effect looks like a swarm of drones.

### Final Recap

A frame buffer is an array of bytes, a pixel is an offset, a circle is sine and cosine, perspective is a division and rotation is two multiplications. With these bricks, and the discipline of verifying every generated or copied line, you have everything you need to build your first 3D engine.
